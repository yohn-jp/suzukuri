# Suzukuri 0.2.1

## Summary

0.2.1 adds ordered multi-step command definitions to `.suzukuri/commands.json`
and a guided `suzukuri init` flow that inspects a repository's existing
test/verify interfaces, proposes a migration to Suzukuri's command contract,
and applies the accepted changes.

## Added

- Ordered `steps` command definitions in `.suzukuri/commands.json`, alongside
  the existing single-`argv` producer form. Steps execute in declared order
  over the existing bounded process execution primitive and stop on the
  first failed/signaled step, matching `&&` aggregate semantics.
- Structural per-step failure identification for `suzukuri verify`: the
  failing step is reported from execution structure (declared step
  name/order), not inferred from concatenated producer output.
- Deterministic execution-result reuse for multi-step command definitions:
  the existing semantic-result cache key now covers step name, order, and
  argv, so changing any step invalidates reuse for that command.
- `suzukuri init`: an interactive repository-adoption flow that:
  - detects the repository/package ecosystem supported by the initial
    implementation (Node.js/pnpm);
  - inspects existing canonical `test`/`verify` package scripts and resolves
    their underlying producer commands;
  - proposes the resulting `.suzukuri/commands.json`, including lossless
    conversion of a composite `&&` `verify` script into ordered steps where
    it can be parsed safely;
  - proposes adding `suzukuri` as a development dependency when required for
    the public package scripts to remain self-contained after clone +
    install;
  - proposes rewiring public package scripts (`test` → `suzukuri test`,
    `verify` → `suzukuri verify`);
  - shows the complete planned file/script/dependency mutations and requires
    explicit confirmation before writing anything;
  - applies an accepted migration atomically enough that a failure cannot
    leave public scripts pointing at missing Suzukuri configuration, and
    validates the generated configuration after writing;
  - is idempotent on an already-initialized repository, or produces an
    explicit no-op/update plan instead of rewriting silently;
  - reports unsupported/ambiguous script composition explicitly instead of
    rewriting it heuristically, and never emits `test:raw`/`verify:raw`
    escape-hatch scripts.

## Changed

- Suzukuri's own `.suzukuri/commands.json` and the Wabachi repository are
  migrated onto the ordered-steps command contract via `suzukuri init`,
  preserving their existing validation stages under `suzukuri test` /
  `suzukuri verify`.
- `suzukuri skill` scenarios are now projected directly from the command
  contract instead of a separately maintained scenario list, so scenario
  usage/help text stays in sync with the actual command surface. Scenario
  output gained structured fields (`title`, `whenToUse`, `scope`, `workflow`,
  `contractReferences`, `invariants`) and is bounded to 4096 bytes per
  response. `--format` now defaults `skill` output to human-readable text
  instead of JSON; pass `--json`/`--format json` for the automation contract.

## Upgrade

```bash
npm install --global suzukuri@0.2.1
suzukuri --version
suzukuri init
```

Expected version output:

```text
0.2.1
```

## Release verification

Publishing is triggered by GitHub Release `v0.2.1` and uses npm Trusted
Publishing through the repository's release-triggered publish workflow. The
workflow rebuilds, tests, packs one tarball, runs
`scripts/verify-release-certification.mjs` against it (release tag, checked-
out source SHA, and tarball digest all match), smoke-tests that same
tarball, and publishes those bytes to npm.
